private static <T> T borrow(Map<Class<T>, Set<T>> pool,
                           Class<? extends T> codecClass) {
  T codec = null;

  // Check if an appropriate codec is available
  Set<T> codecSet;
  synchronized (pool) {
    codecSet = pool.get(codecClass);
  }

  if (codecSet != null) {
    synchronized (codecSet) {
      if (!codecSet.isEmpty()) {
        codec = codecSet.iterator().next();
        codecSet.remove(codec);
      }
    }
  }

  return codec;
}

private static <T> T borrow(ConcurrentMap<Class<T>, NavigableSet<T>> pool,
  Class<? extends T> codecClass) {
  if (codecClass == null) {
    return null;
  }

  NavigableSet<T> codecSet = pool.get(codecClass);
  if (codecSet != null) {
    // If a copy of the codec is available, pollFirst() will grab one.
    // If not, it will return null.
    return codecSet.pollFirst();
  } else {
    return null;
  }
}

private static <T> boolean payback(Map<Class<T>, Set<T>> pool, T codec) {
  if (codec != null) {
    Class<T> codecClass = ReflectionUtils.getClass(codec);
    Set<T> codecSet;
    synchronized (pool) {
      codecSet = pool.get(codecClass);
      if (codecSet == null) {
        codecSet = new HashSet<T>();
        pool.put(codecClass, codecSet);
      }
    }

    synchronized (codecSet) {
      return codecSet.add(codec);
    }
  }
  return false;
}

private static <T> boolean payback(ConcurrentMap<Class<T>, NavigableSet<T>> pool, T codec) {
  if (codec != null) {
    Class<T> codecClass = ReflectionUtils.getClass(codec);
    Set<T> codecSet = pool.computeIfAbsent(codecClass,
      k -> new ConcurrentSkipListSet<>(Comparator.comparingInt(System::identityHashCode)));
    return codecSet.add(codec);
  }
  return false;
}

Summary

My thesis is that the less we use the garbage collector, the better. Every allocation on the heap incurs several costs:

  1. Time is spent to allocate the object, assuming it doesn't fit in the thread-local allocation buffer. If there isn't heap pressure, this takes some cycles but isn't terrible. If there is heap pressure, then you get an allocation stall, which is very damaging to request latency.
  2. Time is spent to clean up the object when it's no longer used. Garbage collection is hard work, and it uses a lot of our CPU cycles. The less garbage we generate, the less needs to get cleaned up, and the more CPU cycles can be devoted to handling user requests.
  3. Access to on-heap byte[] by native code requires taking a lock that blocks the garbage collector. This can incur a JNI critical section stall while a thread waits for that lock. In HBase, this presents when we use libzstd-jni for HFile decompression, and the ByteBuff provided to us by the ByteBuffAllocator is an on-heap buffer. The less often we use on-heap ByteBuffs, the less JNI critical section stalls we get, and the less often they slow down request handling.
  4. In the way the JDK is written, system calls that read or write to userspace memory always interact with direct (off-heap) ByteBuffers. For example, if an on-heap ByteBuffer is passed as the output buffer to a FileChannel read, internally a direct ByteBuffer is actually used, and the result is copied back to your on-heap buffer. If you can pass a direct ByteBuffer to the JDK, it will use it directly and avoid a copy.

See details below for how I'm making changes related to one of more of these bullet points.

ZStandard decompression

Decompression is a very hot path in HBase. Any little inefficiency is obvious on a CPU profile. This section was a campaign to reduce allocations made and unnecessary copies incurred around the decompression process. Ideally during an HBase block read, direct ByteBuffs are used for the block data, and reads and writes go directly to that ByteBuffs. In the case of decompression, HBase gives us a ByteBuff of compressed data, and a ByteBuff for the uncompressed result to go in. My work passes these memory regions straight through to libzstd-jni, and also does some miscellaneous performance enhancements. Solves for bullet points 1, 2, and 3.

  • HBASE-28485: Re-use ZstdDecompressCtx/ZstdCompressCtx for performance
  • HBASE-29123: A faster CodecPool for HBase
  • HBASE-29135: ZStandard decompression can operate directly on ByteBuffs
  • HBASE-29172: Fix bug in ZstdByteBuffDecompressor
  • HBASE-29193: Allow ZstdByteBuffDecompressor to take direct ByteBuffer as input and heap ByteBuffer as output, or vice versa
  • HBASE-29218: Reduce calls to Configuration#get() in decompression path

Row seeking

Row seeking is another extremely hot path. Even tiny allocations here add up a lot. I've eliminated a few. Solves for bullet points 1 and 2.

  • HBASE-29252: Reduce allocations in RowIndexSeekerV1
  • HBASE-29253: Avoid allocating a new closure on every row processed by StoreScanner

Less on-heap buffers

The less byte[] we have on heap, the better, as you can read about in the intro. This section is about reducing sources of on-heap buffers, so we can get the benefits of using direct buffers.

  • No threshold to use direct ByteBuffs from ByteBuffAllocator. By default, the ByteBuffAllocator wants to allocate on-heap buffers when a small buffer is requested, and used a pooled direct buffer when a large enough buffer is requested. In practice, there are plenty of direct buffers in the pool, and no reason not use them as much as possible. Reduce the threshold to use a direct buffer down to 0 bytes. This solves for bullet point 1, 2, and 3.
  • No hedged reads in the DFSClient. In principal, hedged reads are a good idea. If a read from a DataNode is taking longer than a certain threshold, more reads are launched in parallel to the DataNodes hosting the other replicas of that block. In practice, using hedged reads incurs extra byte[] allocations and copies, even in the fast path where no secondary reads are launched. If hedged reads are disabled, and the first DataNode attempted is local, the read will short-circuit. If you've passed a direct ByteBuffer to the DFSInputStream as your output buffer, as we do, this will get threaded all the way into the pread system call. This solves for bullet points 1, 2, and 4.
